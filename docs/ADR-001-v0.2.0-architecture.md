# ADR-001 — v0.2.0 self-hosted local web app architecture

**Status:** Accepted
**Date:** 2026-05-02 (Session 4)
**Decision-makers:** Milan (product owner), Claude (cowork mode session)
**Branch:** `dev/v0.2.0`

---

## Context

v0.1.x of Ultimate Job Assist runs entirely inside Claude Desktop's Cowork mode. The user opens the Ultimate Job Assistant folder, Claude reads the SKILL.md files, and the orchestrator workflow runs against the user's filesystem. This works well for the project's original sole-user audience and ships at $0/mo cost.

The v0.2.0 vision adds a SECOND way to run the same toolkit: a self-hosted local web app the user runs on their own computer, brings their own Anthropic API key to, and uses through a browser tab the same way they use Cowork mode today. Path A (Cowork) and Path B (web app) become two surfaces over the same `skills/[name]/SKILL.md` files. The web app is not a replacement; both paths coexist.

Key user-facing requirements:

- Browse, preview, and manage all generated materials (resumes, decoded JDs, scores, speaking points, cover letters, interview-prep PWAs, portfolio projects, networking drafts) inside the same UI as the chat.
- Same on-disk folder structure as Path A — the web app reads from and writes to the same `Ultimate Job Assistant/` folder Cowork mode operates on.
- Conversations survive restarts; the user can pick up where they left off.
- Bring-your-own-key: no shared backend, no SaaS, no operator infrastructure.
- Distribution must work for non-developer users.

This ADR records ten decisions covering the architecture stack and the configuration model. The first nine answered the open architectural questions raised at the start of Session 4; D10 was added when Milan asked for a UI-driven configuration model.

---

## Quality bar

**v0.2.0 ships as a polished product, not an MVP.** This is a contract that informs every phase below — investment in visual polish, UX completeness, accessibility, performance, and packaging is built into the work, not a separate "polish pass" at the end.

Concretely, every UI surface ships with:

- **Empty states** — what does the materials browser look like before any application has been run? What does the chat pane look like on a fresh project?
- **Loading states** — skeleton placeholders for slow operations (initial chat, file preview), not blank screens.
- **Error states** — helpful messages for the realistic failure modes (API key invalid, network down, project root missing, sandbox boundary violation, model returns 5xx).
- **Keyboard navigation** — `cmd/ctrl+k` for command palette, `cmd/ctrl+enter` to send, `escape` to close modals, arrow-key navigation in lists.
- **Accessibility** — semantic HTML, focus ring visible, color contrast meets WCAG AA, screen-reader labels on icon-only buttons.
- **Performance** — first paint under 1s on a fresh page load; PDF.js / mammoth lazy-loaded only when a file of that type is opened; chat streaming feels instant (no buffering above ~200ms latency).

Distribution gets the same treatment: the launch script must feel professional, not hacky — clear progress messages, friendly error reporting, and a clean shutdown when the user closes the browser tab.

This is informed by Milan's directive: "I want this to be close to final product." That intent is recorded here so future-me reading the ADR knows the bar isn't "ship something that works" — it's "ship something Milan would feel comfortable showing other people."

## Decisions

### D1 — Skill execution surface: Skills-as-Tools

**Decision:** Skills stay as Markdown specs (no code port). The host process registers a fixed tool catalog with the Anthropic API and chats with Claude exactly the way Cowork mode does. The agent loop stays inside Claude.

**Tool catalog (initial):**

| Tool | Purpose |
|---|---|
| `read_file(path)` | Read a file under the project root |
| `write_file(path, content)` | Create or overwrite a file under the project root |
| `edit_file(path, find, replace)` | In-place edit (string replacement, fail if not unique) |
| `list_files(path, glob?)` | Directory listing with optional glob filter |
| `run_skill(name, inputs?)` | Invoke a `skills/[name]/SKILL.md` workflow with optional inputs |
| `propose_changes(diff)` | Surface a proposed multi-file diff for user approval before applying |
| `ask_user(question, options?)` | Multi-choice or free-text question to the user |
| `read_workspace_metadata()` | Returns project root path, current branch, etc. |

The host enforces the file sandbox (D5) at the tool layer.

**Rejected alternatives:**

- **Re-implement the orchestrator in Python.** Each `SKILL.md` step becomes a Python function; the host process IS the agent loop. Tighter and faster, but loses the "skills are markdown specs anyone can edit" property and forks the agent loop from where it already lives (inside Claude). Rejected.
- **Hybrid (some skills as code, some as Markdown).** Splits the model and complicates testing. Rejected.

**Consequences:**

- Cowork mode and web-app mode share the SKILL.md source of truth, so a skill change ships to both surfaces simultaneously.
- The host has a small, stable surface area (eight tools) and the heavy lifting stays in Claude.
- Future skill additions only require a new `skills/[name]/SKILL.md` — no code change.

### D2 — Backend: Python + FastAPI

**Decision:** Python 3.11+ with FastAPI for the host process.

**Rationale:** The toolkit is already heavily Python — `sync_to_public.py`, `scan_pii.py`, `generate_template_resume.py`, `build_pwa.py`, the resume DOCX manipulation, the PDF generation are all Python. The only non-Python piece is `smoke_test.cjs`. Going Python lets the backend reuse existing `scripts/` unchanged. The Anthropic Python SDK is mature and has full streaming + tool-use support.

**Rejected alternatives:**

- **Node + Express/Fastify.** Anthropic Node SDK is also mature, and JS ecosystem alignment with the React frontend is convenient. But every existing Python helper would need to be re-implemented or shelled out to from Node, fragmenting the runtime. Rejected.
- **Go / Rust.** Distribution profile (single binary) is appealing but the developer experience for streaming SSE + tool-use payloads is much worse, and the existing scripts/ would still need a port. Rejected.

**Consequences:**

- `scripts/` directory becomes the backend's lib/.
- Distribution requires the user to have Python 3.11+ (D6).
- Server runs as a single process; no async multi-process complexity.

---

### D3 — Frontend: React + Vite + Tailwind + shadcn/ui

**Decision:** React 18 + TypeScript + Vite + Tailwind CSS + shadcn/ui component library, scaffolded using the patterns from `anthropic-skills:web-artifacts-builder`.

**Rationale:** The chat UI + materials tree + multi-format preview pane benefits significantly from a component model. shadcn/ui gives a polished design system out of the box, so the app looks like a real product from day one rather than a hobbyist React app. The web-artifacts-builder skill has an `init-artifact.sh` script that bootstraps a project with React + TS + Vite + Tailwind 3.4.1 + shadcn/ui + 40+ components pre-installed and `@/` path aliases — we'll use it as the seed.

**Rejected alternatives:**

- **SvelteKit.** Smaller bundles and similar DX, but less ecosystem density for the preview libraries (PDF.js, mammoth, marked) and fewer copy-pasteable chat-UI examples. Rejected.
- **Vanilla HTML + Tailwind CDN** (matches the existing public website stack). Workable for the chat pane alone, but the materials browser + multi-format preview gets ugly without a component model — you'd be reinventing parts of React in vanilla. Rejected.

**Consequences:**

- Frontend has its own `npm install` + Vite dev server during development.
- Production build is a static `dist/` directory the FastAPI backend serves alongside the API.
- "Avoid AI slop" guideline from the web-artifacts-builder skill applies: no excessive centered layouts, purple gradients, uniform rounded corners, or Inter font.

### D4 — Material previews: client-side via PDF.js / mammoth / marked

**Decision:** The backend streams raw bytes for any file the user opens in the materials browser. Rendering happens client-side:

| Format | Library |
|---|---|
| PDF | PDF.js |
| DOCX | mammoth (text extraction → render as styled HTML) |
| Markdown | marked |
| HTML | rendered in iframe with sandbox |
| Plain text | `<pre>` |

**Rationale:** Keeps backend simple (read + stream bytes; no rendering). Client-side rendering means the user can preview a file the moment the backend writes it, with no round trip for a server-rendered preview.

**Consequences:**

- DOCX preview is approximate (mammoth doesn't perfectly preserve every Word feature). Acceptable for review/skim; the user opens the file in Word for high-fidelity edits.
- PDF.js and mammoth bundle sizes are non-trivial; they're loaded lazily only when the user opens a matching file.

### D5 — File access scope: hard sandbox to one project root

**Decision:** At first launch, the user picks ONE folder via a native folder picker (the Ultimate Job Assistant folder they already use with Cowork mode). The backend persists that path. Every file-tool call (D1) validates that the resolved absolute path stays within the project root. No traversal outside.

**Implementation:**

- Resolve the requested path via `pathlib.Path.resolve()`, then check `is_relative_to(project_root)`. Reject otherwise.
- Symlinks within the project root are followed normally; symlinks pointing outside are rejected.
- The project root path is stored in the SQLite DB (D7) and never overridable per-request.

**Rejected alternatives:**

- **No sandbox / open-ended file access.** Trivially exfiltrates anything from the user's home directory if a malicious skill or instruction-injection lands. Rejected.
- **Per-conversation sandbox.** Adds complexity without clear benefit. The toolkit's scope IS one project folder. Rejected.

**Consequences:**

- A user with multiple Ultimate Job Assistant folders runs separate instances. Acceptable.
- Path resolution must always go through the host's sandbox helper — no raw `open(path)`.

### D6 — Distribution: curated-zip extension + start scripts

**Decision:** Extend the existing `scripts/sync_to_public.py` curated zip pipeline. The zip carries:

- All existing `skills/`, `references/`, etc. (already shipped).
- New: `start-uja.sh` (macOS / Linux) and `start-uja.bat` (Windows). On run, the script:
  1. Verifies Python 3.11+.
  2. Creates a virtualenv if one doesn't exist.
  3. Installs the host package + dependencies.
  4. Launches the FastAPI server bound to `127.0.0.1:0` (random ephemeral port).
  5. Opens the user's default browser to the chosen URL.

**Prereq:** Python 3.11+ on the user's machine. Documented in QUICKSTART.md.

**Rejected alternatives:**

- **`pipx install uja` (PyPI distribution).** Cleaner upgrade story but adds a PyPI release pipeline, requires the user to install `pipx` (extra step), and creates a friction tier for non-developer users. Rejected for v0.2.0; reasonable as a parallel channel later.
- **Single binary (PyInstaller / Tauri / Electron).** Zero-prereq install but 50–150 MB per platform, three platform builds required, much heavier release pipeline, breaks the existing curated-zip simplicity. Reasonable as a v0.3.0+ option.

**Consequences:**

- `ZIP_INJECT_FILES` and `ZIP_REQUIRED_MEMBERS` in `sync_to_public.py` grow to include the start scripts and the host source.
- The start script is the only thing the user sees on first run; it must be robust on macOS, Linux, and Windows. Tested on all three before tag.

### D7 — Persistence: SQLite at the project root, schema-versioned

**Decision:** Single SQLite file at `<project-root>/.uja/state.db`. Schema is versioned via a `schema_version` table; migrations are forward-only. The DB stores:

| Table | Purpose |
|---|---|
| `schema_version` | Current schema version |
| `conversations` | One row per chat thread with title, started_at, updated_at |
| `messages` | Append-only chat history (role, content, tool_calls, tool_results, ts) |
| `tool_invocations` | Per-tool-call audit log (cross-references messages) |
| `settings` | Key-value store for user preferences (project root, theme, etc.) |
| `keychain_pointer` | Reference to OS keychain entry where the API key is stored |

**Rationale:** Single file, durable, queryable, no extra dependencies (Python's `sqlite3` is stdlib). Append-only message log makes export/inspection trivial. Schema versioning lets us evolve the data model without breaking existing installs.

**Rejected alternatives:**

- **JSON files per conversation.** Human-readable but messier to query at scale and hard to keep consistent if multiple windows/tabs are open. Rejected.
- **In-memory only.** Loses the resume-where-I-left-off use case. Rejected.

**Consequences:**

- `.uja/` is gitignored (added to the user-facing `.gitignore` template in `references/zip-bundle/`).
- Conversations and tool history are accessible to other tools running on the same machine. Acceptable since it's local-only.

### D8 — API key handling: OS keychain + 127.0.0.1-only

**Decision:** Three coordinated rules:

1. **API key encrypted at rest** via the OS keychain — Python's `keyring` library (uses macOS Keychain, Windows Credential Manager, libsecret on Linux). The DB stores only a pointer to the keychain entry, never the key itself.
2. **API key never logged.** Logging filters drop any string that matches `sk-ant-...` or related prefixes. Tool invocation logs (D7) redact request/response payloads that include the key.
3. **Server binds 127.0.0.1 only by default.** Refuses connections from any other interface. A documented `--bind` override exists for power users who want to expose to LAN, but it's never the default.

**Rationale:** A local web app holding a paid API key is a credential-leak target. Keychain at rest + localhost-only over the wire + log redaction in transit covers the realistic threat model (other processes on the same machine, accidental log uploads, casual-attacker LAN scans).

**Consequences:**

- First-run flow asks the user to paste their Anthropic API key, validates with a test API call, then stores it via `keyring`.
- Re-pasting the key (rotation) is a settings-page action; the keychain entry is overwritten in place.
- Server logs are safe to share for debugging.

### D9 — Branch protection: local pre-push hook (Pro-gated workaround)

**Decision:** GitHub branch protection / rulesets are Pro-gated on free private repos (verified via API: HTTP 403 with "Upgrade to GitHub Pro"). Rather than pay $4/mo for Pro, the project ships a local pre-push hook at `references/git-hooks/pre-push` that refuses direct pushes to `main`. `scripts/install-hooks.sh` is the idempotent installer; each clone runs it once after cloning canonical.

The hook prints a clear error message pointing at the PR flow and notes that `--no-verify` is the bypass for genuinely intentional pushes (e.g., merging an approved PR locally).

**Note:** This is local-side enforcement only. The auto-sync GitHub Action runs on a hosted runner where the hook is not installed, so workflow-driven pushes (auto-sync to deploy-source) are unaffected. That's the intended behavior.

**Rationale:** Catches the realistic failure mode (muscle-memory `git push` from a local checkout that happens to be on `main`) at $0 cost. Also documented in SPEC.md §13 decision 11.

### D10 — Configuration model: Settings tab + Materials tab (two-tier)

**Decision:** All user-facing configuration is reachable through the UI. The configuration surface is split across two tabs:

**Settings tab — how the app behaves:**

| Field | Notes |
|---|---|
| Anthropic API key | With "Test connection" button. Stored via OS keychain (D8). |
| Project root | Folder picker. Changing it requires a confirm + server restart. |
| Default model | Sonnet / Opus / Haiku, with cost-estimate hint per model. |
| Theme | Light / dark / system. |
| Keyboard shortcuts | `cmd+k`, `cmd+enter`, `esc`, customizable. |
| Auto-update tracker | On / Off / Always-ask. |
| Cover letter sign-off | Text input; persisted to `memory.md` Sign-off section. |
| Network bind override | `127.0.0.1` default; `0.0.0.0` toggle for power users. |
| Notifications | OS-native notifications for long-running skill completion. |
| Clear chat history | Destructive action with confirm. Drops the SQLite `messages` table. |
| Export all data | Zip of project root + DB. |
| About | Version, links to docs, "send feedback" mailto. |

**Materials tab — your content the app reads and writes:**

- **`memory.md` editor** — full-screen rich markdown editor (CodeMirror with markdown mode + live preview side-by-side). Sections (Identity, Key stories, Resume preferences, Sign-off) are highlighted in a navigation rail. Auto-saves on edit. The file is still `memory.md` on disk; the editor is a polished view over it.
- **`tracker.md` view** — table or kanban view of applications, NOT a markdown textarea. Columns: company, role, status, skills run, decisions log. Edits are point-and-click and persist back to `tracker.md` (round-trip preserves file-based portability).
- **Skill specs viewer** — read-only view of every `skills/[name]/SKILL.md` so power users can see exactly what each skill does. Edit lives in the user's text editor of choice (link out to the file path).
- **Application archive** — browse past applications by company / role with previews of every output type (resume, scores, speaking points, cover letter, etc.).

**Rejected alternatives:**

- **Pure Settings tab.** Crams `memory.md` story content into Settings textareas, which discourages thoughtful narrative writing and feels like "filling out a form" instead of "telling your story." Rejected.
- **No in-app editing.** User edits `memory.md` and `tracker.md` in their own text editor; the app is read-only over them. Simplest to build but worse daily UX. Rejected — fails the polish bar.
- **Hybrid where some `memory.md` sections are in Settings.** Splits the file's editing across two tabs, which is confusing and brittle if the file is edited externally. Rejected.

**Rationale:**

- The user's instruction was explicit: configurable through a Settings tab. Settings tab is the canonical app-config surface.
- BUT `memory.md` is not configuration — it's the user's narrative voice. A polished markdown editor with live preview belongs in Materials, not Settings.
- AND `tracker.md` is structured data — a table view edits faster than a markdown table.
- File-based portability is preserved everywhere: edits round-trip to disk so you can copy the project folder between machines or open it in Obsidian / VSCode without losing anything.

**Consequences:**

- The frontend has at least three primary tabs (Chat, Materials, Settings) plus per-skill action panels.
- The CodeMirror dependency is added in Phase 17 (lazy-loaded only when Materials → memory.md is opened).
- The tracker UI is non-trivial; budget for it explicitly in Phase 17.

## Phasing impact (cross-reference SPEC.md §14)

This ADR is the deliverable for **Phase 14**. The remaining v0.2.0 phases:

- **Phase 15:** Backend scaffold (FastAPI, project-root picker, `/api/chat` streaming endpoint, file-sandboxed tool endpoints). On `dev/v0.2.0`.
- **Phase 16:** Skill registry — every `skills/[name]/SKILL.md` registered as an Anthropic tool. Run the existing Netflix end-to-end regression entirely through the web app and structurally diff outputs against v0.1.0 snapshots. On `dev/v0.2.0`.
- **Phase 17:** React + Vite + Tailwind + shadcn/ui frontend (chat pane, materials browser, multi-format preview). On `dev/v0.2.0`.
- **Phase 18:** Distribution — cross-platform launch script, curated-zip integration, QUICKSTART recipe. On `dev/v0.2.0`.
- **Phase 19:** Comprehensive testing — unit (tool definitions, message-loop reducer, sandbox boundary), integration (orchestrator on a fixture application; assert exact file outputs), E2E (Playwright through full chat flow + filesystem assertions), manual (Milan runs ONE real upcoming application end-to-end and writes a SESSION_LOG entry covering rough edges).
- **Phase 20:** Docs refresh — top-level CLAUDE.md gains a "Web App Mode" section; `references/zip-bundle/CLAUDE.md` gets a "First Session in Web App Mode" block parallel to the existing "First Session Behavior — Detect Fresh Install And Onboard"; ONBOARDING.md grows a Path A (Cowork) vs Path B (web app) split; QUICKSTART.md gets a launch recipe.
- **Phase 21:** Merge gate — final review, run all tests once more on the merge candidate, squash-merge or merge-commit `dev/v0.2.0` into `main` only when Milan signs off.
- **Phase 22:** Tag `v0.2.0`.

## Open questions deferred from v0.2.0

- **Multi-conversation routing.** The DB schema supports multiple conversations per project, but the v1 frontend can ship with only the latest conversation surfaced and a "history" affordance added later. Not blocking.
- **OAuth-style API key alternative.** Some users may prefer to log into Anthropic via OAuth rather than paste a raw key. Not in scope for v0.2.0; reasonable v0.3.0+ enhancement.
- **Multi-window concurrency.** If two tabs are open against the same project root, they could clash on tool writes. v0.2.0 ships with a "single active session" lock and surfaces a warning if a second tab tries to write.
- **Code execution inside the PWA.** Already deferred to ROADMAP.md Track 3.
